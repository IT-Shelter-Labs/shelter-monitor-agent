# Shelter Monitor Agent: подробное руководство

[На главную](../README.md) · [English](../README_EN.md)

Лёгкая self-hosted система мониторинга Linux-сервера с интерфейсом в Telegram.
Подходит для домашнего сервера и VPS.

- **Ресурсы:** CPU, RAM, swap, диски, load average, температура, аптайм, сетевой трафик, доступ в интернет.
- **Docker:** остановленные, перезапускающиеся и `unhealthy` контейнеры, появление и удаление контейнеров.
- **systemd:** заданные сервисы и любые юниты в состоянии `failed`.
- **SSH:** успешные входы, перебор паролей с одного IP, массовые атаки с многих IP, успешный вход после серии неудач.
- **Кто стучался:** сканирование портов по логам файрвола (UFW/iptables), внешние подключения к опасным
  портам (RDP, VNC, базы данных, Docker API), сводка «Безопасность за 24 часа».
- **LAN:** уведомления о новых устройствах в локальной сети (Docker-сети автоматически исключаются).
- **Падение сервера:** heartbeat во внешний сервис (Healthchecks.io с уведомлением в Telegram — без своего
  второго сервера) или в `shelter-watchdog`; после включения агент сам сообщает, сколько сервер был
  недоступен, и предполагает перезагрузку или аварийное завершение по сохранённым отметкам. Точную причину аппаратного сбоя агент не устанавливает.
- **Telegram-бот:** статус, метрики, контейнеры (логи, запуск, перезапуск), сервисы, SSH, безопасность,
  события, устройства, уведомления, проверка по запросу и самодиагностика `/diag`.
- **Действия с подтверждением:** перезапуск сервисов и контейнеров, запуск/остановка контейнеров, очистка Docker,
  перезапуск агента — только заранее определённые операции над разрешёнными объектами, с подтверждением.

Агент написан на Python. На Python 3.11+ достаточно стандартной библиотеки; на 3.10 нужен `tomli` (установщик ставит `python3-tomli`). psutil и Docker SDK не используются. События и настройки уведомлений хранятся в SQLite. Расход ресурсов зависит от сервера, числа контейнеров и настроек.

## Архитектура

```
┌──────────────────────── сервер (shelter-agent) ────────────────────────┐
│                                                                        │
│  collectors/          monitors/             ssh.py        lan.py       │
│  /proc, /sys    ──►   resources        ┐    journald /    ARP-опрос    │
│  Docker socket  ──►   docker_watch     │    auth.log      подсети      │
│  systemctl      ──►   services_watch   │       │             │         │
│  TCP connect    ──►   connectivity     │       ▼             ▼         │
│                                        └──►  EventBus  ──► SQLite      │
│                         AlertTracker ──────►    │        (события,     │
│                         (только смена          ▼          SSH, LAN)    │
│                          состояния)        Notifier ──► Outbox ──► Telegram
│                                                                  ▲     │
│  bot/ (long polling) ◄── команды и кнопки администратора ────────┘     │
│  actions.py — разрешённые действия с подтверждением                    │
│  heartbeat.py ── POST /api/v1/heartbeat ──┐                            │
└───────────────────────────────────────────┼────────────────────────────┘
                                            ▼
                  ┌──── другая машина (shelter-watchdog) ────┐
                  │ нет heartbeat N минут → тревога в Telegram│
                  └───────────────────────────────────────────┘
```

Устройство проекта:

```
shelter_monitor/
├── telegram.py            # клиент Bot API на urllib + очередь отправки с rate limit и повторами
├── util.py                # форматирование, загрузка TOML
├── agent/
│   ├── app.py             # сборка компонентов и жизненный цикл
│   ├── cli.py             # shelter-agent run | check-config | test-telegram | get-chat-id | status | sudoers
│   ├── config.py          # TOML → dataclasses с валидацией
│   ├── storage.py         # SQLite (WAL): events, ssh_auth, devices, kv
│   ├── events.py          # Event, EventBus, AlertTracker (алерты только при смене состояния)
│   ├── notifier.py        # фильтры уведомлений: важность, категории, mute
│   ├── scheduler.py       # периодические задачи, по одному потоку на монитор
│   ├── collectors/        # system (/proc, /sys), docker (unix socket), systemd (systemctl show)
│   ├── monitors/          # пороги ресурсов, Docker, сервисы, связь
│   ├── logsources.py      # чтение journald (journalctl -f -o json) и syslog-файлов с учётом logrotate
│   ├── ssh.py             # парсер sshd, детектор перебора
│   ├── security.py        # сканирования портов по логам файрвола, внешние подключения к опасным портам
│   ├── lan.py             # обнаружение устройств в LAN (без Docker-сетей)
│   ├── heartbeat.py       # отправка heartbeat
│   ├── actions.py         # фиксированный набор действий с подтверждением
│   ├── runtime.py         # контейнер или хост, сеть хоста, собственный контейнер
│   ├── diagnostics.py     # самодиагностика (/diag)
│   └── bot/               # команды, кнопки, экраны
└── watchdog/              # внешний приёмник heartbeat (зачаток Shelter Monitor Hub)
```

Каждый монитор — независимый класс с методом `tick()` и выдаёт объекты `Event`.
Новый монитор подключается одной строкой в `agent/app.py`. События имеют стабильную форму
(`Event.to_dict()`), а heartbeat-сообщение уже содержит идентификатор агента, версию и сводку метрик.
Это основа для будущего центрального Hub (см. [дорожную карту](#дорожная-карта)).

## Требования

- Основной сценарий: Ubuntu 22.04+ или Debian 12+. На других Linux-дистрибутивах нужно отдельно проверить зависимости, пути к журналам и systemd; установщик использует apt.
- Для запуска в Docker: Docker Engine с плагином `docker compose` на самом наблюдаемом Linux-сервере.
  Docker Desktop для macOS и Windows не подходит.
- Для установки без Docker:
  - Python 3.10+. Он уже есть в системе. На Python 3.10 установщик сам поставит `python3-tomli`;
  - `sudo` — только если нужен перезапуск сервисов из Telegram.

## Запуск в Docker (docker compose)

Образ один для агента и watchdog. Он собирается из `Dockerfile` на основе `python:3.13-slim`
и дополнительно содержит только `systemctl` и `journalctl` из пакета `systemd`.
Агент следит за **хостом**, поэтому в [`docker-compose.yml`](../docker-compose.yml) контейнеру выдан
доступ к нужным частям хоста:

| Что подключено | Зачем |
|---|---|
| `network_mode: host` | трафик интерфейсов, проверка связи, ARP-таблица и обнаружение устройств в LAN |
| `/` → `/host` (только чтение) | диски хоста, `/etc/os-release`, имя хоста |
| `/var/run/docker.sock` | состояние контейнеров и перезапуск из `[actions].containers` |
| `/run/systemd` (только чтение) | статус сервисов systemd хоста (`systemctl` из образа обращается к systemd хоста) |
| `/var/log`, `/run/log/journal`, `/etc/machine-id` (только чтение) | логи SSH из journald или `/var/log/auth.log` |
| `/etc/localtime` (только чтение) | часовой пояс хоста для времени в сообщениях |
| том `shelter-data` | база SQLite (`/var/lib/shelter-agent`) |

CPU, память, load average, аптайм и температура читаются из `/proc` и `/sys`: в контейнере это данные
ядра хоста. Если какое-то подключение убрать, соответствующая функция просто отключится.

### Пошагово

1. Склонируйте репозиторий на сервер, который нужно мониторить:
   ```bash
   git clone https://github.com/IT-Shelter-Labs/shelter-monitor-agent.git
   cd shelter-monitor-agent
   ```
2. Создайте конфиг из примера:
   ```bash
   cp config/agent.example.toml config.toml
   chmod 600 config.toml
   ```
3. Создайте бота у [@BotFather](https://t.me/BotFather) и узнайте свой Telegram ID:
   ```bash
   docker compose build
   docker compose run --rm shelter-agent agent get-chat-id --token 123456:ABC...
   ```
   Напишите боту любое сообщение — в терминале появится ваш `user id`. Остановите команду через Ctrl+C.
   Подробнее — в разделе [Настройка Telegram-бота](#настройка-telegram-бота).
4. Впишите токен и ID в `config.toml`:
   ```toml
   [telegram]
   token = "123456:ABC..."
   admin_ids = [123456789]
   ```
   Остальные параметры можно оставить по умолчанию (см. [Конфигурация](#конфигурация)).
   Пути внутри контейнера (`data_dir`, `log_file`, `socket`) менять не нужно.
5. Запустите агента:
   ```bash
   docker compose up -d
   docker compose logs -f
   ```
   В Telegram придёт сообщение «Агент мониторинга запущен», а `/status` покажет сводку по серверу.

Полезные команды:

```bash
docker compose ps                                              # статус и healthcheck
docker compose exec shelter-agent shelter-agent check-config   # проверить конфиг
docker compose exec shelter-agent shelter-agent test-telegram  # тестовое сообщение
docker compose exec shelter-agent shelter-agent status         # метрики хоста в терминале
docker compose restart shelter-agent                           # применить изменения config.toml
```

Обновление: `git fetch --tags`, выбор нужного тега через `git checkout`, затем `docker compose up -d --build`. Данные в томе `shelter-data` сохраняются.
Удаление: `docker compose down`. Чтобы удалить и базу данных, добавьте флаг `-v`.

### Особенности работы в контейнере

- **`network_mode: host` обязателен.** Если добавить агента в свой compose-проект с секцией `networks:`,
  он окажется во внутренней Docker-сети: «устройствами LAN» станут соседние контейнеры, трафик и
  входящие подключения будут чужими. Агент это распознаёт и пишет в `/diag`. Правильно — отдельный
  сервис без `networks:` (или отдельный `docker-compose.yml`, как в репозитории):
  ```yaml
  services:
    shelter-agent:
      image: shelter-monitor:latest
      network_mode: host          # не сочетается с networks:
      # ... остальное — как в docker-compose.yml из репозитория
  ```
- Если что-то показывается неверно (сервисы «не установлены», диски контейнера, нет SSH-событий),
  откройте в боте **🩺 Диагностика** (`/diag`): там видно, какого подключения не хватает и как его добавить.

- **Перезапуск сервисов systemd из Telegram** (`[actions].services`) в контейнере работает без sudo.
  Но systemd хоста требует от вызывающего процесса `CAP_SYS_ADMIN`, поэтому раскомментируйте строку
  `- SYS_ADMIN` в `cap_add` файла `docker-compose.yml`. Без неё статус сервисов показывается,
  а перезапуск — нет. Перезапуск контейнеров (`[actions].containers`) работает в любом случае.
- Правило sudoers и `shelter-agent sudoers` в Docker не нужны.
- Контейнер работает от root с урезанным набором capabilities (`cap_drop: ALL` + `DAC_READ_SEARCH`),
  корневой ФС только для чтения, `no-new-privileges` и лимитом памяти 200 МБ.
  Учтите, что доступ к `docker.sock` фактически равен root-доступу к хосту.
  Если Docker-мониторинг не нужен, удалите эту строку и задайте `[docker].enabled = false`.
- Состояние контейнера отслеживает Docker healthcheck (`shelter-agent healthcheck`):
  `docker compose ps` покажет `unhealthy`, если агент завис.
- Watchdog в Docker описан в разделе [Heartbeat](#вариант-со-своим-сервером-shelter-watchdog-входит-в-проект).

## Установка без Docker (systemd)

```bash
git clone https://github.com/IT-Shelter-Labs/shelter-monitor-agent.git
cd shelter-monitor-agent
git checkout v0.1.0
sudo ./scripts/install.sh
```

Установщик:

- копирует код в `/opt/shelter-monitor`;
- создаёт команды `/usr/local/bin/shelter-agent` и `/usr/local/bin/shelter-watchdog`;
- создаёт системного пользователя `shelter` без shell и добавляет его в группы:
  - `adm` — для чтения `/var/log/auth.log`;
  - `systemd-journal` — для чтения journald;
  - `docker` — если Docker установлен. Чтобы не добавлять, используйте флаг `--no-docker-group`;
- создаёт конфиг `/etc/shelter-agent/config.toml` (права `0640 root:shelter`), если его ещё нет;
- устанавливает и включает `shelter-agent.service`. Сервис запустится, как только конфиг станет валидным.

Затем настройте Telegram (следующий раздел) и запустите сервис:

```bash
sudo shelter-agent check-config      # проверка конфига
sudo shelter-agent test-telegram     # тестовое сообщение
sudo systemctl restart shelter-agent
journalctl -u shelter-agent -f
```

## Настройка Telegram-бота

1. Создайте бота у [@BotFather](https://t.me/BotFather) командой `/newbot` и скопируйте токен.
2. Узнайте свой Telegram ID:
   ```bash
   sudo shelter-agent get-chat-id --token 123456:ABC...
   ```
   Напишите боту любое сообщение — команда выведет ваш `user id`.
   Другой способ: запустите агента и отправьте боту `/id`.
3. Укажите токен и ID в `/etc/shelter-agent/config.toml`:
   ```toml
   [telegram]
   token = "123456:ABC..."
   admin_ids = [123456789]
   ```
   Токен можно хранить отдельно: `token_file = "/etc/shelter-agent/telegram.token"` (права 0640 root:shelter)
   или передать через переменную окружения `SHELTER_TELEGRAM_TOKEN`.
4. Чтобы уведомления приходили в группу, добавьте бота в группу и укажите её ID в
   `notify_chat_ids = [-100...]`. ID группы показывает `get-chat-id`.
   Командами в группе могут пользоваться только пользователи из `admin_ids`.

Если `api.telegram.org` недоступен, укажите HTTP(S)-прокси (`proxy = "http://host:port"`)
или адрес собственного Bot API сервера (`api_url`).

## Конфигурация

Полный пример с комментариями — [`config/agent.example.toml`](../config/agent.example.toml).
Основные секции:

| Секция | Назначение | По умолчанию |
|---|---|---|
| `[agent]` | имя сервера, каталог данных, срок хранения | имя = hostname, хранение 30 дней |
| `[telegram]` | токен, администраторы, чаты для уведомлений, прокси | — |
| `[notifications]` | минимальная важность, поведение при mute | `warning`; критические приходят и при mute |
| `[monitor]` | пороги CPU/RAM/swap/диска/load/температуры | CPU 90% в течение 2.5 мин, RAM 90%, диск 85/95% |
| `[docker]` | сокет, какие контейнеры отслеживать | все контейнеры |
| `[services]` | список юнитов systemd, отслеживание failed | `ssh`, `cron`, `docker` |
| `[connectivity]` | проверка интернета TCP-подключением | `1.1.1.1:53`, `8.8.8.8:53` |
| `[ssh]` | источник логов, порог перебора, доверенные сети | 10 попыток за 5 мин |
| `[firewall]` | анализ логов файрвола, порог сканирования портов | 10 разных портов за 2 мин |
| `[connections]` | внешние подключения к опасным портам | RDP, VNC, СУБД, Docker API и др. |
| `[lan]` | обнаружение устройств | подсеть основного интерфейса, раз в 5 мин |
| `[heartbeat]` | внешний heartbeat | выключен |
| `[actions]` | разрешённые действия | все контейнеры, сервисы из `[services]`, очистка Docker, перезапуск агента |

Как работают уведомления:

- Алерты отправляются только при **смене состояния**: при возникновении проблемы, повышении её важности
  и восстановлении (с длительностью). Пока проблема сохраняется, агент не шлёт повторных сообщений.
- События `info` (например, появление нового контейнера) записываются в журнал, но не рассылаются.
  Исключения, которые приходят всегда: SSH-входы, новые устройства в LAN, восстановления,
  а также запуск и остановка агента (без звука).
- Контейнер, который был остановлен ещё при запуске агента, алерта не вызывает. Алерт будет,
  если контейнер работал и остановился, или если он явно указан в `[docker].watch`.
- `/mute` и переключатели категорий хранятся в базе и сохраняются после перезапуска агента.

### SSH

По умолчанию (`source = "auto"`) агент читает journald (`journalctl -f -o json`) для идентификаторов
`sshd` и `sshd-session`; последний используется в OpenSSH 9.8+. Если journald недоступен, агент читает
`/var/log/auth.log` и учитывает logrotate. Позиция чтения сохраняется, поэтому входы,
случившиеся во время перезапуска агента, не теряются.

Агент отправляет уведомления о следующих событиях:

- успешный вход (кроме входов из `trusted_networks`);
- **подбор пароля**: `bruteforce_threshold` неудач с одного IP за `bruteforce_window` секунд.
  По одному IP повторное уведомление приходит не чаще раза в `bruteforce_cooldown`;
- **массовая атака**: в 5 раз больше неудач со многих IP за то же окно;
- **🚨 успешный вход после ≥3 неудач с того же IP** — критическое событие.

Агент не блокирует IP: для этого есть fail2ban или CrowdSec. Shelter Monitor уведомляет и показывает статистику.

### LAN

Агент отправляет пустой UDP-пакет на каждый адрес подсети, чтобы ядро выполнило ARP-разрешение,
а затем читает `/proc/net/arp`. Ни root, ни raw-сокеты, ни nmap не нужны.
Первое сканирование задаёт базовый список: все найденные устройства считаются известными.
О каждом новом MAC-адресе приходит уведомление с кнопкой «✅ Доверять».
Случайные (приватные) MAC-адреса телефонов отмечаются отдельно.
Подсети больше `max_hosts` адресов активно не опрашиваются. Публичные подсети VPS автоматически не сканируются.
Подсети Docker-сетей (`docker network ls`) исключаются, а уже записанные из них «устройства» удаляются.
В уведомлении о новом устройстве кнопки «✅ Доверять» и «🗑 Забыть» меняют само сообщение;
в `/devices` есть «Доверять всем» и «Забыть все».

### Кто стучался на сервер

| Что | Откуда | Уведомление |
|---|---|---|
| Вход по SSH | journald / `auth.log` | каждый успешный вход (кроме `trusted_networks`) |
| Подбор пароля SSH | journald / `auth.log` | N неудач с одного IP, массовая атака, вход после серии неудач |
| Сканирование портов | логи файрвола (UFW/iptables) | один IP перебрал ≥ `scan_ports` портов за `scan_window` |
| Подключение к опасному порту | `/proc/net/tcp` | новое внешнее соединение к RDP/VNC/СУБД/Docker API… |
| Новое устройство в сети | ARP-таблица | новый MAC в локальной сети |

Для анализа сканирований нужен включённый файрвол с логированием заблокированных пакетов. Правила доступа на удалённом сервере настройте заранее; агент не включает файрвол автоматически:

```bash
sudo ufw logging low     # для уже настроенного UFW: писать блокировки в журнал
```

Сводка за сутки — команда `/security` (кнопка «🛡 Безопасность»).
Контроль подключений не видит порты, опубликованные из Docker-контейнеров (`ports:` в compose):
такие соединения обрабатываются в сетевом пространстве контейнера.

## Команды бота

| Команда | Что делает |
|---|---|
| `/status`, `/start` | сводка: проблемы, CPU/RAM/диски, Docker, сервисы, SSH, heartbeat; меню-кнопки |
| `/metrics` | подробные метрики: диски, сетевые интерфейсы (скорость), задержка до внешних адресов |
| `/docker` | контейнеры; по нажатию — карточка: логи, запуск, перезапуск, остановка |
| `/services` | состояние сервисов, команда установки для отсутствующих, кнопки перезапуска |
| `/ssh` | последние входы, неудачные попытки за 24 ч, топ IP |
| `/security` | безопасность за сутки: SSH, файрвол, внешние подключения, неизвестные устройства |
| `/events` | последние важные события (кнопка «Показать все») |
| `/devices` | устройства в LAN: доверять, забыть, внеочередное сканирование |
| `/check` | «Проверить всё»: выполнить все проверки сейчас, не дожидаясь расписания |
| `/diag` | самодиагностика: что агент видит, чего не хватает и как это исправить |
| `/notify` | mute на 1/8/24 часа, включение и выключение категорий |
| `/mute 2h`, `/unmute` | выключить или включить уведомления (формат `30m`, `2h`, `1d`) |
| `/actions` | все доступные действия |
| `/id` | ваш ID и ID чата (доступна всем — нужна для первоначальной настройки) |

Бот не принимает свободный текст и не выполняет произвольные команды.

**«Проверить всё»** — агент выполняет проверки по расписанию (ресурсы раз в 30 с, сервисы раз в минуту,
LAN раз в 5 минут). Кнопка запускает их все немедленно и показывает итог: какие проблемы появились,
какие исчезли, и актуальный статус. Полезно после того, как вы что-то починили.

## Действия

Набор операций фиксирован в коде, а объекты для них ограничены конфигом на сервере.
Изменить конфиг из Telegram нельзя. По умолчанию доступно:

| Действие | Где в боте | Что разрешено по умолчанию |
|---|---|---|
| Перезапуск / запуск / остановка контейнера | `/docker` → контейнер; кнопки под алертом | все контейнеры (`containers = ["*"]`), кроме остановки самого агента |
| Логи контейнера (последние 40 строк) | там же | все контейнеры, без подтверждения |
| Перезапуск сервиса systemd | `/services`, `/actions`; кнопка под алертом | сервисы из `[services].units` и `[actions].services` |
| Очистка Docker (образы без тегов, кэш сборки) | `/actions`, `/docker`; кнопка под алертом «мало места» | включено |
| Перезапуск агента | `/actions` | включено |

Ограничить набор можно так:

```toml
[actions]
containers = ["nextcloud", "web-*"]   # только эти контейнеры; [] — ни одного
container_stop = false
allow_monitored_services = false       # сервисы — только из списка ниже
services = ["nginx"]
docker_prune = false
agent_restart = false
```

Порядок работы: кнопка действия → сообщение «Подтвердите действие» с предупреждением о последствиях
(например, «перезапуск Docker перезапустит все контейнеры») → «✅ Подтвердить». Подтвердить может только
тот, кто запросил, и только в течение `confirm_timeout`. Если время вышло, кнопки исчезают сами.
Результат и автор действия попадают в журнал событий и рассылаются всем администраторам.
Повторить то же действие можно не раньше чем через 30 секунд.

**Установка пакетов из бота не предусмотрена.** Это произвольное изменение системы вне фиксированного
набора действий, и из контейнера оно невозможно в принципе. Для отсутствующего сервиса `/services`
показывает команду установки (например, `sudo apt install cron`). Его также можно убрать из `[services].units`.

**Сервисы.** Агент работает от пользователя `shelter` и перезапускает сервис командой
`sudo -n systemctl restart <unit>`. Разрешите ровно эти команды:

```bash
sudo shelter-agent sudoers | sudo tee /etc/sudoers.d/shelter-agent
sudo visudo -cf /etc/sudoers.d/shelter-agent
```

Сгенерированное правило выглядит так:
`shelter ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx.service`.
После изменения `[actions].services` создайте файл заново.

В Docker sudo не нужен: раскомментируйте `SYS_ADMIN` в `docker-compose.yml`
(см. [особенности работы в контейнере](#особенности-работы-в-контейнере)).

**Контейнеры** управляются через Docker API (`POST /containers/<name>/restart|start|stop`).

Чтобы полностью отключить действия, задайте `[telegram].allow_actions = false`.

## Heartbeat и обнаружение падения сервера

Агент на упавшем сервере не может сообщить о собственном падении: Telegram сам ничего не отправит,
кто-то снаружи должен заметить тишину. Поэтому сервер периодически сообщает внешнему наблюдателю
«я жив», а если сообщения перестают приходить, тревогу поднимает наблюдатель.

### Без второго сервера: Healthchecks.io + Telegram (рекомендуется)

[Healthchecks.io](https://healthchecks.io) — внешний сервис проверки heartbeat с интеграцией Telegram. Доступные тарифы и лимиты уточняйте на сайте сервиса.

1. Зарегистрируйтесь на healthchecks.io.
2. **Integrations → Telegram**: по ссылке на странице откройте их бота, отправьте ему `/start`
   (или добавьте в группу) и подтвердите подключение.
3. **Add Check**: Period — 1 минута, Grace — 3–5 минут. Скопируйте Ping URL вида `https://hc-ping.com/<uuid>`.
4. В конфиге агента:
   ```toml
   [heartbeat]
   enabled = true
   method = "GET"
   url = "https://hc-ping.com/<uuid>"
   interval = 60
   ```
5. Перезапустите агента. В `/diag` строка Heartbeat станет ✅, а через несколько минут проверка на сайте позеленеет.

Если сервер перестанет отвечать дольше Period + Grace, в Telegram придёт сообщение от бота Healthchecks
(не от вашего бота: ваш бот работает на упавшем сервере), а после восстановления — сообщение «up».
Аналогично работают Uptime Kuma (push-монитор), Cronitor, Better Stack Heartbeats:
задайте их URL с `method = "GET"`.

### Встроенный отчёт после восстановления

Агент каждые 30 секунд отмечает в базе «я жив» и отдельно записывает штатную остановку. После старта он
сравнивает эти отметки с моментом загрузки системы и присылает одно из сообщений:

- 🚨 **Сервер был выключен или завис** — штатной остановки не было (пропало питание, kernel panic,
  жёсткий сброс). Указаны последний признак жизни, время загрузки и длительность простоя.
- ⚠️ **Сервер был перезагружен** — штатная перезагрузка, тоже с длительностью простоя.
- ⚠️ **Агент был аварийно остановлен** — сервер работал, а сам агент не работал (например, был убит).

Отчёт требует сохранившейся базы данных и повторного запуска агента. Он не заменяет heartbeat: о падении вы узнаете только после восстановления.

### Вариант со своим сервером: Shelter Watchdog (входит в проект)

Установите его на **другую** машину: дешёвый VPS, Raspberry Pi в другом месте и т.п.

```bash
git clone https://github.com/IT-Shelter-Labs/shelter-monitor-agent.git
cd shelter-monitor-agent
git checkout v0.1.0
sudo ./scripts/install.sh --watchdog
shelter-watchdog gen-token            # токен для каждого сервера
sudo nano /etc/shelter-watchdog/config.toml
sudo systemctl restart shelter-watchdog
```

```toml
# /etc/shelter-watchdog/config.toml
[watchdog]
port = 8787
default_timeout = 300        # 5 минут без heartbeat → тревога

[telegram]
token = "123456:ABC..."      # можно того же бота: watchdog только отправляет сообщения
chat_ids = [123456789]

[[agents]]
id = "home-server"
name = "Домашний сервер"
token = "<вывод gen-token>"
```

На наблюдаемом сервере:

```toml
[heartbeat]
enabled = true
url = "https://watchdog.example.com/api/v1/heartbeat"
token = "<тот же токен>"
method = "POST"
interval = 60
```

Через Docker то же самое делается так (на машине для watchdog):

```bash
cp config/watchdog.example.toml watchdog.toml && chmod 600 watchdog.toml   # token, chat_ids, [[agents]]
docker compose -f docker-compose.watchdog.yml run --rm shelter-watchdog watchdog gen-token
docker compose -f docker-compose.watchdog.yml up -d --build
```

В `watchdog.toml` оставьте `listen = "0.0.0.0"`: это адрес внутри контейнера, а наружу
публикуется порт 8787 (настраивается в `docker-compose.watchdog.yml`).

Watchdog присылает «🚨 Сервер не отвечает» с последними известными метриками, а после восстановления —
«✅ снова на связи» с длительностью простоя. Состояние watchdog хранится в
`/var/lib/shelter-watchdog/state.json`. После перезапуска watchdog каждому агенту даётся полный таймаут,
чтобы не было ложных тревог.

Watchdog работает по HTTP. Публикуйте его наружу через TLS-прокси, чтобы токены не передавались открытым
текстом. Пример для Caddy:

```
watchdog.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

При установке watchdog как systemd-сервиса задайте `listen = "127.0.0.1"`. В Docker оставьте `listen = "0.0.0.0"` внутри контейнера и замените публикацию порта в compose на `"127.0.0.1:8787:8787"`. API watchdog:

- `POST|GET /api/v1/heartbeat` — заголовок `Authorization: Bearer <токен агента>`;
- `GET /api/v1/status` — заголовок `Authorization: Bearer <status_token>`, ответ — JSON со всеми агентами;
- `GET /healthz`.

## Модель безопасности

- **Нет произвольного shell.** Бот понимает только фиксированный набор команд и кнопок. Свободный текст
  игнорируется, внешние процессы запускаются с фиксированным argv, без `shell=True`.
- **Авторизация по Telegram user ID.** Сообщения и нажатия кнопок от пользователей не из `admin_ids` отклоняются.
  Такие попытки записываются в журнал событий (с ограничением частоты).
- **Изменяющие действия:** только фиксированные операции (перезапуск/запуск/остановка, очистка Docker,
  перезапуск агента) над объектами, разрешёнными в конфиге (его нельзя изменить из Telegram;
  по умолчанию — все контейнеры и отслеживаемые сервисы, это легко сузить).
  Каждое действие требует подтверждения тем же пользователем через одноразовый токен с ограниченным сроком
  жизни. Действия выполняются по одному, повтор возможен не раньше чем через 30 секунд, всё записывается
  в аудит. Имена юнитов и контейнеров проверяются строгими регулярными выражениями.
- **Минимальные права.** Агент работает от системного пользователя `shelter`.
  Права для перезапуска сервисов выдаются через sudoers на `systemctl restart` конкретных юнитов. Членство в группе `docker` отдельно даёт широкие права на хосте.
  systemd-юнит включает `ProtectSystem`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`,
  `ProtectKernel*`, `RestrictNamespaces`, `MemoryMax`.
  `NoNewPrivileges` не включён, потому что иначе не будет работать `sudo`.
  Если действия с сервисами не нужны, включите его через override
  (`sudo systemctl edit shelter-agent`):
  ```ini
  [Service]
  NoNewPrivileges=yes
  ```
- **Docker:** доступ к `docker.sock` фактически равен root-доступу. Если это неприемлемо, установите агент с
  `--no-docker-group` и отключите `[docker]`, либо не подключайте сокет к контейнеру и отключите `[docker].enabled`. Клиент агента принимает путь к Unix-сокету; HTTP endpoint прокси не поддерживается.
- **Секреты:** установщик задаёт конфигу права `0640 root:shelter`; база создаётся с правами `0600`. В Docker конфиг создаётся пользователем: задайте `chmod 600 config.toml`. Токен бота не попадает в логи
  и тексты ошибок, а `check-config` выводит секреты замаскированными.
- **Watchdog** запускается с максимальной изоляцией (`NoNewPrivileges`, `ProtectSystem=strict`, пустой
  `CapabilityBoundingSet`). Он ограничивает размер тела запроса и сравнивает токены за константное время.

## Диагностика

| Симптом | Решение |
|---|---|
| Сервис не стартует | `journalctl -u shelter-agent -e`; `sudo -u shelter shelter-agent check-config` |
| `HTTP 409` в логе | этот токен опрашивает другой процесс (второй агент или `get-chat-id`). У каждого агента должен быть свой бот |
| Нет SSH-событий | проверьте `id shelter` (группы `adm`, `systemd-journal`) и источник в `/ssh`; после изменения групп выполните `systemctl restart shelter-agent` |
| `/docker`: нет доступа | пользователь `shelter` не в группе `docker` или задан другой `socket` |
| Перезапуск сервиса: `a password is required` | не установлено правило sudoers (см. [Действия](#действия)) |
| Ложные алерты о диске для snap/overlay | добавьте шаблон в `[monitor].disk_ignore` |
| Telegram заблокирован | `[telegram].proxy` или `api_url` |
| Docker: на месте `config.toml` появилась папка | файл не был создан до `docker compose up`. Удалите папку и выполните `cp config/agent.example.toml config.toml` |
| Docker: в `/status` диски контейнера, а не хоста | не подключён `/:/host:ro,rslave` |
| Docker: нет SSH-событий | проверьте подключения `/var/log`, `/run/log/journal`, `/etc/machine-id` и строку `SSH:` в стартовом сообщении |
| Docker: перезапуск сервиса — `Access denied` | раскомментируйте `SYS_ADMIN` в `docker-compose.yml` |
| Сервисы «не установлены», хотя установлены | откройте `/diag`: обычно нет доступа к systemd хоста (в Docker — том `/run/systemd`). Теперь вместо «не установлен» показывается настоящая ошибка, а статус берётся по процессам хоста |
| «Новые устройства» вида `172.x.x.x` с именами контейнеров | агент запущен во внутренней Docker-сети — нужен `network_mode: host`. Эти записи удаляются автоматически |
| Нет данных о сканированиях | `sudo ufw logging low`; проверьте `/diag` → «Файрвол» |

Где лежат данные: `/var/lib/shelter-agent/agent.db` (SQLite). Пример запроса:
`sudo sqlite3 /var/lib/shelter-agent/agent.db 'select * from events order by id desc limit 10'`.

## Разработка

```bash
python3 -m unittest discover -s tests -t . -v   # тесты (только stdlib)
ruff check shelter_monitor tests                 # линтер
shellcheck scripts/*.sh
```

Тесты покрывают парсинг `/proc` и логов sshd, детекторы, state machine алертов, фильтры уведомлений,

Чтобы добавить монитор:

1. Создайте класс с атрибутами `name`, `interval` и методом `tick()`, который вызывает
   `tracker.check(key, firing, make_event, make_resolved)` или `bus.emit(Event(...))`.
2. Зарегистрируйте его в `Agent.__init__` (`agent/app.py`).
3. При необходимости добавьте экран в `bot/views.py` и команду в `bot/bot.py`.

## Дорожная карта

- **Shelter Monitor Hub:** развитие `shelter-watchdog` в центральный сервис для нескольких серверов.
  Агенты будут отправлять события (`Event.to_dict()`) вместе с heartbeat, а Hub — вести единый
  Telegram-бот, веб-панель и историю метрик. Поля `agent_id`, `schema` и `seq` уже есть в payload.
- История метрик и графики в боте.
- Мониторинг SMART и RAID (`smartctl`, `/proc/mdstat`), проверки SSL-сертификатов и HTTP-эндпоинтов.
- Deb-пакет.
